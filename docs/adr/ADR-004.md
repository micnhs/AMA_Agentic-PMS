## Context

Cases, signals and audit must work the same locally without cloud and in Azure; the audit trail must be
tamper-evident and immutable.

## Options

- **A** – Azure Cosmos DB for NoSQL (serverless) plus a hash chain in the app.
- **B** – Azure SQL with ledger tables.
- **C** – Azure Confidential Ledger.

## Decision

Proposal **A**: locally SQLite with triggers against `UPDATE` and `DELETE`; in Azure Cosmos DB
serverless, the audit container only with a custom data role without replace and delete, local keys
disabled; letters and reports in Blob Storage.

## Consequences

The hash chain (SHA-256 over the previous hash and the record) makes changes detectable; subscription
owners can still delete resources (limit stated in the README). B and C are more expensive or additional
services.

## Implementation in this repository (not part of the concept text)

- Offline: `src/pms/audit.py` appends records to SQLite; triggers abort every `UPDATE` and `DELETE` on
  the audit table. `verify()` recomputes the chain and reports the first break.
- Azure (`infra/modules/cosmos.bicep`): database `pms` with the containers `cases`, `signals`, `records`
  and `audit` (partition key `/pk`; unique key `/seq` on `audit`). The app identity has the built-in
  Data Contributor role only on `cases`, `signals` and `records`, and a custom role
  *PMS audit append-only* on `audit` (read metadata, create items, read items, query, read change
  feed – no replace, upsert or delete). Local (key) authentication is disabled.
- `src/pms/azure/cosmos_store.py` keeps the semantics of the SQLite store: `cases` and `signals` hold
  one document per case or signal; `records` holds every other table as documents typed by table name,
  plus the analysis-job queue, ID counters, meta values, a short write lease (it serialises
  read-check-write steps of the web app and the worker) and the published Foundry agent versions;
  `audit` holds one document per record (`id` = sequence number, partition `audit-chain`), written with
  create only. Writes use optimistic concurrency. Cosmos DB has no multi-document rollback: a failure
  inside a step leaves the writes made so far, and the audit chain stays valid.
- Letters, reports and copies of the alert e-mails are stored in the Blob containers `letters`, `reports`
  and `outbox` (no public access, shared key disabled).
- Check the chain with `bash scripts/verify-audit.sh` (offline) or `bash scripts/verify-audit.sh --azure`.
