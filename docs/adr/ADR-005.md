## Context

In Azure, roles must come from Microsoft Entra ID; locally, the offline mode needs test users.

## Options

- **A** – Entra app registration with app roles created by Bicep (Microsoft Graph extension) plus the
  built-in authentication of Container Apps.
- **B** – Bring your own app registration.
- **C** – Own authentication in the app.

## Decision

Proposal **A**, with **B** as a parameter fallback when the deployer may not create app registrations.
No client secret (ID-token flow); Azure resources only through managed identities. Local test users only
when `APP_ENV=local`; the app does not start in Azure when `LOCAL_TEST_USERS` is active.

## Consequences

The preflight checks the Entra rights and names the fallback in plain words (OI-013).

## Requirement R-19 (concept v1.1)

Sign-in only through Microsoft Entra ID: built-in authentication of Container Apps (single tenant,
sign-in enforced), app roles from the token, no local accounts in Azure; multi-factor authentication
through the tenant's Conditional Access (design element D-39).

## Implementation in this repository (not part of the concept text)

- `infra/modules/entra-app.bicep` creates a single-tenant app registration with the app roles
  `PMS.Viewer`, `PMS.Analyst`, `PMS.Regulatory`, `PMS.MedicalReviewer` and `PMS.Operator`, the scope
  `user_impersonation`, ID tokens and v2 access tokens, and a service principal with
  *assignment required* (users without an app role cannot sign in).
- `infra/modules/container-apps.bicep` configures built-in authentication (redirect to the login page,
  issuer `https://login.microsoftonline.com/<tenant>/v2.0`); only `/healthz` is excluded.
- Bring your own: `azd env set ENTRA_EXISTING_APP_CLIENT_ID <client-id>` (optionally
  `ENTRA_EXISTING_APP_IDENTIFIER_URI`). The postprovision hook prints the redirect URI and the settings
  the registration needs. The teardown script never deletes a bring-your-own registration.
- `scripts/postprovision.*` pre-authorises Azure CLI for the API scope (so that the seed and smoke-test
  scripts can get a token) and assigns the deployer the roles in `DEPLOYER_APP_ROLES`
  (default `PMS.Operator`).
- `src/pms/auth.py` reads the principal that the built-in authentication passes on
  (`X-MS-CLIENT-PRINCIPAL`) and maps the app roles to the domain roles; without it a request gets `401`.
  In Azure the demo-user header and cookie are ignored, and the app refuses to start with
  `LOCAL_TEST_USERS=true` (also under a WSGI server).
- Offline, the built-in test users `viewer`, `analyst`, `regulatory`, `reviewer` and `operator` (one per
  role) exist only when `APP_ENV=local` and `LOCAL_TEST_USERS=true`. The browser picks one on `/login`
  (cookie `pms_demo_user`, `HttpOnly`, `SameSite=Strict`); scripts send the header `X-Demo-User`.
- What a user may do is decided only by the workflow's role matrix; refused attempts are recorded as
  `ACCESS_DENIED`.
