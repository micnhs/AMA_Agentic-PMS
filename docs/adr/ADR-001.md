## Context

The Goal Card requires agents on Microsoft Agent Framework (MAF) with a Foundry client and an offline
stand-in behind one interface, and a Foundry project with Foundry Agent Service.

## Options

- **A** – Prompt agents in Foundry Agent Service, created as versions from the repository and called
  through MAF `FoundryAgent`.
- **B** – Agents owned by the app through MAF `FoundryChatClient` (Responses endpoint of the project);
  prompts only in the repository.
- **C** – Hosted agents (containers in the Agent Service).

## Decision

Decided on 10 Nov 2026 (Q-5): **A**. Agent versions are visible in the Foundry portal and can be
referenced in the audit trail. B remains the documented fallback behind the same interface. C is not used.

## Consequences

Agents get no tools; registry, dossier and corpus data are supplied by deterministic code. According to
the Microsoft Learn table (read on 10 Nov 2026), gpt-5.4-mini does not support function tools in the
Agent Service; research therefore runs as a workflow loop ([ADR-007](ADR-007.md)). Structured outputs
for prompt agents are to be confirmed in Stage 2 (OI-011).

## Translation note

The consequence text above is carried over unchanged from concept v0.2, when gpt-5.4-mini was the
proposed model. Since concept v0.3, decisions Q-9 and Q-10 replaced that model ([ADR-002](ADR-002.md),
requirement R-18), and the design gives agents A2, A3 and A6 **read-only function tools** (corpus,
dossier, registry and case search). The app code validates every argument against a schema and an
allow-list, executes the call itself, limits the number of calls per run and writes every call to the
audit trail (design element D-31; concept sections 3.4, 6.1 and 6.5). There are still no tools that
write, send or decide. Where this ADR and the later sections differ, the later decisions apply.

## Implementation in this repository (not part of the concept text)

- One agent interface with two implementations: the deterministic offline stand-in (fixed, versioned
  answers and token counts, no network) and the Foundry adapter (Microsoft Agent Framework with
  Foundry Agent Service). Code: `src/pms/agents/`.
- The Azure-only packages (`agent-framework-core`, `agent-framework-foundry`, pinned in
  `requirements.txt`) are imported lazily inside the adapter, so the offline mode needs only the
  Python standard library.
- Each agent run records agent name and version, model deployment and version, prompt version and token
  usage in its audit record (concept section 8, design element D-21).
- The Foundry adapter (`src/pms/agents/foundry.py`) builds each agent with `FoundryChatClient`,
  publishes it as a Foundry prompt agent (`project.agents.create_version`) only when its specification
  changed (fingerprint of prompt, model deployment, tools, response schema and project; the published
  version per agent is kept in Cosmos DB `records`) and runs the published version with `FoundryAgent`
  (at most 10 minutes per run, retries with backoff for transient errors). The app identity has the role
  *Azure AI User* on the Foundry account, so publishing on first use needs no extra step;
  `python -m pms publish-agents` (postdeploy hook, worker start) publishes changed agents explicitly
  (Azure settings and the Azure packages required).
